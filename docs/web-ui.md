# Задача: Web UI — Stage 1. Knowledge Map

Добавь в репозиторий `learning-template` первую версию локального Web-интерфейса для просмотра процесса обучения.

Перед реализацией изучи структуру проекта, текущую модель Knowledge Graph, класс `Repository` и способы чтения связанных данных. Максимально используй существующую функциональность.

## Архитектура

- Весь код Web UI размещай в новой папке `web/`.
- Backend: Python + FastAPI.
- Frontend: React + React Flow.
- Источник данных — текущий локальный репозиторий.
- Приложение работает исключительно на чтение.
- Не создавай базу данных.
- Не изменяй существующий учебный движок и формат данных.
- Не добавляй поддержку нескольких репозиториев или Git-веток.

## Функциональность первого этапа

**1. Knowledge Map**

- Отображать существующие Graph Nodes и связи.
- Основная навигация — иерархия, основанная только на реальных `part-of` связях (дочерний узел → родитель). Типы `area`, `topic`, `concept` не создают дополнительных связей.
- Узлы можно раскрывать и сворачивать.
- По умолчанию показывать иерархические связи.
- Предусмотреть переключатели для отображения `prerequisite` и `related` связей.
- Добавить поиск по названию узла с переходом к найденному элементу.

**2. Панель выбранного Node**

При выборе узла показывать:

- Название, тип, описание и место в иерархии.
- Связанные Graph Nodes.
- Связанные Units, найденные по существующей модели данных.
- Активные Gaps, если их связь с узлом можно достоверно установить.

Не вычисляй новый показатель mastery для Node. Не подменяй его оценками связанных Units.

**3. Просмотр Unit**

Реализуй простую страницу Unit, доступную из панели Node:

- Название и описание.
- Текущий статус Progress.
- Результаты по `recall`, `understanding`, `application`, если они имеются.
- Связанные Nodes и активные Gaps.

Используй существующие данные без новых алгоритмов оценки.

## Технические требования

- Backend переиспользует существующий Python-движок там, где это возможно.
- Не дублируй учебную бизнес-логику во Frontend.
- API предоставляет данные в удобном для визуализации формате.
- У Node и Unit должны быть постоянные URL.
- Интерфейс должен корректно обрабатывать отсутствие отдельных данных.
- Предусмотри простой локальный запуск, желательно одной командой после установки зависимостей.
- Добавь краткую инструкцию по установке и запуску.

## Что пока не реализовывать

- Dashboard.
- Learning History.
- Редактирование данных.
- Запуск Study, Practice или Review.
- Новые расчёты Progress и mastery.
- Авторизацию и синхронизацию.

## Согласованные правила первого этапа

- Демонстрационные данные находятся в `web/fixtures/demo/`; включаются только явным `--demo`. Обычный запуск читает корень текущего репозитория и для `uninitialized` показывает сообщение без подстановки демоданных.
- У Node с несколькими родителями есть отдельное визуальное представление под каждым родителем, но общий Graph ID, URL и данные.
- Узел без родителей показывается в корне независимо от типа.
- Повтор Node в текущей ветви обозначается как циклическая ссылка и не раскрывается дальше. Компоненты с циклами без корня доступны отдельно; никакие Nodes не теряются.
- Связанные Units определяются только прямым вхождением `node.id` в `unit.nodes`. Связанные Gaps определяются только `gap.node == node.id`; активны только `detected` и `confirmed`. Данные потомков не агрегируются.
- Инициализированные Units из `units/` и запланированные Skeleton Units только из Frontier показываются раздельно. Запланированные помечаются `Planned`, без Progress. При совпадении ID используются реальные данные Unit, запись показывается один раз и может отмечаться присутствие во Frontier.
- Описание Node берётся из `summary`, Unit — из `goal`. Отсутствующий Progress не заменяется вычисленным статусом.
- Для обновления достаточно refresh браузера. Backend читает данные заново при каждом запросе, без кеша, WebSocket, watcher и polling.
- Демо содержит несколько Units, Gaps, Progress и специальные случаи иерархии. После rebase интерфейс проверяется на `education_branch`.

## Критерий готовности

После запуска приложения пользователь может открыть браузер, увидеть Knowledge Graph текущего репозитория, раскрыть интересующую область, выбрать Node, изучить его данные и перейти к связанной Unit.

Работай в `main`. В дальнейшем мы перенесём изменения в `education_branch` через rebase.

По завершении перечисли изменённые файлы, кратко опиши архитектуру и объясни, как вручную проверить основные функции. Не запускай тесты самостоятельно.
